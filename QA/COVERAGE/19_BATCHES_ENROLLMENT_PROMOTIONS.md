## G02 — Enrollment form and transitions

It requires batch active/Open, validates requested active/waitlist capacity, and rejects an existing Active enrollment for that student/batch. It does not reject an existing Waitlisted duplicate. BUG-FUNC-0016: payload has no LifecycleReason field, so every non-Active choice fails the backend reason requirement. Backend accepts status case-insensitively but stores provided casing. Compare SQL collation semantics and frontend exact Active checks; do not assume lowercase rows are ignored by case-insensitive SQL.

BUG-DATA-0006 is extended, not duplicated: Update does not recheck active/waitlist capacity, batch-open state, prerequisites or duplicate enrollment. ## G02 — Promotion form and decision state machine

BATCH-FORM-001 student/source/target selectors are handler-required. Student change clears source but not target; source choices derive only from exact Active enrollment, target excludes selected source but includes inactive/closed/full batches. Changing source can leave an already selected target no longer eligible. effective is required DateOnly; notes optional and trimmed byAPI. Test missing/default/malformed date, before source start, stale source, target became full/closed, foreign IDs, Unicode/long notes and retained typed note after submit. No explicit notes length mapping exists on BatchPromotion.

Create rejects identical source/target, missing active source enrollment or target outside tenant, then stores Pending and returns empty200. Decide accepts exact Approved/Rejected only and scopes promotion to tenant. Approval loads exactly one Active source with SingleAsync, marks it Completed with reason, sets end date, and inserts a target Active enrollment at effective date. There is no effective-date policy guard or target availability/prerequisite/duplicate revalidation. These admission gaps extend BUG-DATA-0006. Missing/duplicate active source is an unhandled exceptional path; verify controlled response and zero writes.

BUG-DATA-0032 covers approved->rejected contradiction and repeated approval. UI hides decisions after Pending/PendingApproval, but server lacks corresponding state guard. Test each current/requested state, duplicate pending requests, stale tabs, lost response, two concurrent approvals and approve/reject race. Source completion, new target row and promotion decision must agree after atomic domain SaveChanges; audit is separately saved (BUG-API-0002). The UI approval prompt treats Cancel as empty optional note and still sends approval; test deliberate cancellation and require explicit no-write acceptance before release. Rejection requires reason in UI only; direct API accepts empty reason. Keep decision confirmation/reason policy explicit.
