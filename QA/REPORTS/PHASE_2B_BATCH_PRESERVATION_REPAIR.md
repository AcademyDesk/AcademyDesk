## Cause and repair

The register sent only visible fields to the complete-record PUT. Hidden batch code, waitlist capacity, delivery mode, schedule, room, enrolment status, notes and end date were reset to defaults/null. Teacher assignment preserved some fields but omitted class type/session length/frequency/teaching-day JSON/meeting link; Online/Hybrid assignment consequently failed required-link validation. API summaries omitted class type, session length/frequency and teaching-day JSON.

[BatchesController](../../apps/api/Controllers/BatchesController.cs) now includes those four fields in list/create/update summaries. Existing constructor arguments retain their positions; appended fields have compatible defaults. Request records, Apply, Validate, future-session teacher synchronization and authorization are unchanged. Real HTTP confirms inherited UpdateBatchRequest optional properties already bind correctly; no DTO-binding rewrite was necessary.

[Shared batch-update helper](../../apps/web/src/lib/batch-update.ts) builds the complete known replacement payload. [Batch register](../../apps/web/src/app/batches/page.tsx) overrides only editable name/course/teacher/branch/capacity/start date or active state; [Teachers Management](../../apps/web/src/app/teachers/page.tsx) overrides only teacher assignment. All other current summary values, including end date, meeting link and optional nulls, are retained. Existing API defaults apply only for unavailable optional summary values.

Raw API PUT remains replacement: callers can explicitly clear nullable fields, and clients that omit them still reset them. This is not server PATCH/optimistic concurrency or protection against old cached clients. Previously lost production settings are not restored. No UI layout, other form feedback/reset/pending behavior or business policy has been changed.
