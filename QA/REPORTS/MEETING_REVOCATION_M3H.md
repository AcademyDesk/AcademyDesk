## Implemented

- Separate local disconnect and provider-revocation meanings. For the current three profiles, the coordinator atomically disconnects the current binding, advances generation/version, stores a unique exchange-bound revocation record and commits required disconnect/start-or-manual audits. Credential material can only be released to the private internal Google handoff after that transaction commits. The revocation record contains protected metadata, not another stored copy of tokens; existing encrypted exchange evidence is retained.
- Current initiating Owner/Admin, academy/module/role/stamp, registration/profile, source exchange integrity and fence, expected binding version, positive decision and current generation are independently checked. Revocation is allowed to address an expired access token's still-potentially-valid refresh grant; access expiry is never reported as revocation. General local-disconnect consent is not Google project-grant consent.
- Google candidate requires **two explicit decisions**: local disconnect and separate project-wide grant revocation. A protected `google-project-grant/1` consent scope binds the decision evidence. Its inactive internal sender uses only the fixed HTTPS revoke endpoint and form-body refresh token, not a token URL/header/model field. The current actor/source/generation is checked again before request and before committing an acknowledgement. Memory single-send material plus durable unique admission prevents coordinator retries/replays; process restart never reconstructs a send permit.
- Bounded 10-second fake-provider request, no application retry. Only an unencoded HTTP 200 with an empty response is conservatively treated as a provider acknowledgement. Error/redirect/429/body/network/cancellation becomes unknown or leaves a durable start marker for recovery. Acknowledgement is **not proof of immediate or global token invalidation**. The secure handler factory remains required for any future activation: no redirect/proxy/cookie shortcuts, normal TLS and bounded headers.
- Current Microsoft and Zoom public-PKCE profiles remain **ManualRequired**, with no token handoff or automatic request. No invented confidential Zoom credential resolver, broad Microsoft session logout, or false revocation success. Recovery cannot promote these records to acknowledged.
- Expired/interrupted Google revocation recovers only to `OutcomeUnknown` with required audit; never requeue/resend. A Google `Started` or `OutcomeUnknown` record blocks new authorization intents for that academy/provider, including after restart. A new grant must not race a pending project-wide revoke. Unknown resolution requires a separately reviewed reconciliation path; there is no force-clear/automatic unlock here.
- SQL persistence: one revocation per exchange; composite academy/provider/actor/exchange and binding foreign keys; status/version and positive-generation constraints; populated downgrade refusal. Denial-only HTTP no-write snapshots include revocations. No public routes/DI, new PENTA tool, UI enablement, live provider access, Connected state, token refresh or credential purge is implemented by this slice.

## Provider protocol review / deliberate limits

Google documents revocation as removing the project grant, potentially affecting tokens for all clients under that project; this is why a generic disconnect acknowledgement is insufficient. Provider processing/propagation and consent impact must be qualified before enabling the candidate. [Google OAuth revocation](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke).

Microsoft `revokeSignInSessions` invalidates refresh tokens/session cookies broadly and is not a per-application disconnect substitute. This implementation does not request that permission or invoke it. Authorized provider-side permission/consent removal remains a separate workflow. [Microsoft Graph session revocation](https://learn.microsoft.com/en-us/graph/api/user-revokesigninsessions?view=graph-rest-1.0).

Zoom documents Basic client authentication for its revoke request. The accepted candidate here is public-PKCE/no-secret; its revoke authentication/lifecycle is not qualified. It remains manual-required rather than fabricating a confidential-client secret or assuming confidential docs apply unchanged. [Zoom OAuth revoke and public-client documentation](https://developers.zoom.us/docs/integrations/oauth/).

These are conservative code-owned dispositions, not live account qualification. The new coordinator starts from a current quarantined exchange **before** local disconnection. Previously disconnected legacy bindings still need an approved scoped credential resolver/manual workflow; this does not reopen them or bypass the existing generation fence. Future consent must come from an authenticated human decision interface, never model/memory approval claims. Source-account ownership/directory/issuer/entitlement and Google propagation/cross-client/cross-academy grant impact remain independent gates. In particular, an academy admin cannot authorize effects on another academy's shared grant: grant isolation/impact must be qualified before any live sender or registration is enabled. The inactive candidate and its synthetic confirmations are not that infrastructure proof.
