# Phase 2B — Recipient inbox eligibility and separate read acknowledgment

2026-10-01. One bounded local repair of [BUG-FUNC-0027](../ISSUES/BUG-FUNC-0027.md). Issue and Phase 2B remain **OPEN**. Accepted Astra findings were used; no broad repeat audit. Sol High remains suitable.

## Behavior

- GET and PATCH use the same visibility predicate before projecting bodies or writing receipts. Scheduled time must be absent or due (`<=` UTC now). Due InApp Queued messages are available without external transport. Supported InApp/Email/WhatsApp Sent or legacy Read rows remain available as history. Future, Cancelled, BlockedConsent, AwaitingConnection, Failed, RetryRequested and unknown channel/state rows are hidden; guessed hidden IDs return404 without writes.
- Ownership remains academy + signed-in person's ID + matching Student/Teacher/Guardian/Parent recipient type. No new role grants, sender delivery transitions, consent policy, announcement policy or inactive-account/person policy were introduced.
- PATCH saves a separate `NotificationReadReceipt` keyed by notification/account; it never updates Notification.Status, SentAtUtc, schedule, attempts, failure reason or body. Two accounts linked to one person have independent receipts. SQL Server takes an update/hold lock on the notification inside a transaction before checking eligibility/inserting the receipt, serializing concurrent first reads and delivery-row updates. Repeat calls return the original timestamp.
- GET adds `isRead` and nullable `readAtUtc`, keeping existing delivery status intact. Legacy Status=Read is treated as already read for compatibility; its lost prior delivery status/read timestamp cannot be reconstructed. No historical backfill/resend occurs. Identity is a separate EF context: the receipt has a Notification FK and account GUID, not a cross-context Identity FK.
- The learner/parent menu acknowledges only its eight displayed unread items, not unseen messages or closing clicks. It checks HTTP and matching JSON acknowledgment before updating read fields, preserves newer delivery fields/rows, guards in-flight duplicate clicks, retains failed/partial items as unread and shows retry feedback. The existing compatibility fallback understands legacy Read responses when initially listing. A read response lacking the new confirmation fields is not treated as successful.
- Teacher messages use the same GET endpoint; no teacher page/layout changes were needed. Announcements and sender UpdateStatus are not covered by this repair.
