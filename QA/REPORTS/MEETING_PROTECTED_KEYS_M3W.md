## Operational limits — still release gates

[Microsoft key-management documentation](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/implementation/key-management?view=aspnetcore-10.0) and [configuration guidance](https://learn.microsoft.com/en-us/aspnet/core/security/data-protection/configuration/overview?view=aspnetcore-10.0), reviewed2026-10-16: encryption-at-rest does not replace storage access controls; key caches are per process, so another warm replica may not immediately observe revocation. This fixture deliberately uses fresh providers for replacement-key and revocation observations. It does not establish fleet-wide instant revocation.

No real process/container/SQL-server restart, Linux filesystem/volume/certificate/ACL validation, replica propagation, Azure identity/vault/mount provisioning, disaster recovery or production backup/restore was run. A copied key-ring snapshot over the same current disposable database is **not a full database restore**. Production recovery must preserve the matching data/key generations, revocation history and current authority/incident fences; restoring pre-incident keys must not silently undo revocations. No restore/force-clear API or dangerous key-revocation override is added. Key/certificate deletion, retention duration, holds and purging old customer state remain governed operations requiring separate qualification/approval.

Provider-side revocation is separate from Data Protection key revocation. These tests make no claim of external grant removal, valid provider consent/entitlement, live credential rotation or an enabled connection. Existing Google acknowledgement/Unknown reconnect interlocks remain unchanged. Real provider setup/evidence dependencies are retained in [M3v](MEETING_GOOGLE_RECONCILIATION_M3V.md#existing-qualification-inputs--next-handoff).
