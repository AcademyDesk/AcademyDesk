## 6. Proposed shared architecture and reuse protection

**DO NOT REBUILD — REUSE EXISTING** Next.js/manual pages, ASP.NET Core API, both EF contexts, Identity, live role/grant/module checks, existing domain entities, working validation, tested transaction helpers, private Blob abstractions, protected download policy, notification records/preferences, lead/trial APIs, deterministic financial calculations, export infrastructure and established design-system components.

Use one modular intelligence area in the current API initially:

User → authenticated Intelligence Gateway → intent/strict tool schema → scoped context projection → current authorization → risk/approval gate → approved adapter → existing protected application operation → domain validation/transaction/audit → normalized result.

The LLM plans/explains. It cannot grant permission, approve itself, choose a different tenant, issue arbitrary database queries or determine whether its own execution succeeded.

### Gateway and service boundary

Gateway accepts authenticated requests, derives actor and academy on the server, checks academy activity/module entitlement, imposes request/tool limits and permits only allowlisted tools. The five agents are distinct experiences sharing this pipeline, not five services with independent credentials.

Initial adapters may invoke existing HTTP endpoints through the real protected pipeline under the initiating user's authority, with a server-controlled destination and explicit route allowlist. Never call controller methods directly or give adapters an unrestricted DbContext to reproduce mutation logic. Do not persist user bearer tokens for background jobs. If an in-process boundary is needed, extract one selected application operation and its authorization/transaction policy; make both the controller and adapter use it, with equivalence tests. Avoid broad refactoring.

For delayed workflows, store actor identity, approved bounded delegation and scope, not an unlimited service principal. Revalidate current actor, tenant, module, role/grants, targets, consent and approval at execution time. Revocation stops future execution. Cross-tenant platform actions require a separate explicit design and remain excluded initially.

### Academy Brain: structured context, not duplicate ERP storage

People/time/money/learning/sales/resources/history already exist as EF entities. Roles/grants and module policies represent some rules. “Goals” and complete structured academy operating policies are not established as a dedicated model. Build narrow authorized read projections with source IDs, as-of timestamps, timezone and currency. Keep operational data in existing tables. Start without embeddings/vector storage. Retrieval of uploaded text later needs tenant/recipient scopes and prompt-injection handling; private downloads do not automatically authorize model disclosure.

### Approvals and action state

Use risk classes: R0 authorized bounded read; R1 reversible bounded mutation; R2 sensitive money/identity/schedule/external communication; R3 destructive, bulk, permission or irreversible action. Start R1 with confirmation until the capability has accepted safeguards. Exclude R3 initially. Exact thresholds and approver policy need business approval.

Persist an action state machine: Proposed → AwaitingApproval → Approved → Executing → Succeeded / Failed / OutcomeUnknown; plus Rejected, Expired, Cancelled. Approval binds academy, actor/approver, tool/schema version, canonical argument hash, target IDs/count, amount/currency, expected entity versions and expiry. Modified inputs or stale business state require reapproval. Recheck authorization after approval and immediately before mutation. Atomically consume approval with execution claim; prevent replay/concurrent approvers. Cancellation is best effort once execution begins; never label an uncertain external result cancelled.

For same-database writes, commit domain change and attributable action outcome under the proven transaction where feasible. Store failed attempts separately without falsely creating success audits. For external messages use durable intent/outbox and provider reconciliation; a database rollback cannot unsend a message. Timeout means OutcomeUnknown until reconciled, not permission to retry blindly. No universal “undo”: record specific compensating operations with their own authority and audit.

### Audit, privacy, idempotency and costs

Extend, do not replace, domain AuditLog with a correlated AiExecution ledger and append-only attempts/approval events. Preserve actor, academy, agent, tool/version, safe intent summary, redacted arguments, approval, source versions, outcome/error category, model usage and reversal relationship. Raw passwords, tokens, sensitive student/medical content and unrestricted conversations are excluded by default. Retention and access require policy; audit deletion controls cannot silently erase operational proof.

Idempotency key scope: tenant + initiating authority + tool/version + client operation ID, with canonical payload hash and unique database constraint. Reusing a key with different data conflicts. Persist successful result and reconcile uncertain outcomes. Confirm capability-specific concurrent invariants separately: idempotency does not solve two different payment requests consuming the same balance.

Deterministic hierarchy: existing rules → SQL/.NET calculation → events/rules/workflows → small model for intent/formatting → stronger reasoning only for genuinely ambiguous analysis. Server validates model outputs. Set per-tenant/model budgets, tool-call count/time limits, circuit breakers and cancellation. Reserve estimated usage, record actual provider usage, reconcile differences; estimates must not be presented as actual charges. Version price assumptions and plan limits. Engineering model routing is separate from this product runtime router.

Treat user notes, uploaded documents, provider content and tool results as untrusted data, never authority. Test prompt injection, cross-tenant target IDs, excessive result requests, approval forgery and privilege changes between planning/execution. Bind all conversation/cache keys to tenant and actor scope; do not share cached sensitive outputs after permission changes.

### Signals, automation and analytics

Pulse starts with deterministic, permission-scoped signal rules. Give a signal tenant, rule/version, entity key, time window, severity/reason, observed facts/as-of, deduplication key and lifecycle (active/resolved/snoozed). Acknowledge/snooze a signal without marking the underlying invoice/class fixed. No periodic “ask the LLM what is wrong” loop.

Autopilot requires durable workflow definitions, approved scope/version, trigger schedule/timezone, leases, bounded retries/backoff, deduplication, dead-letter/manual recovery, pause/kill switch and auditable execution. Reuse SQL initially for durable work/outbox if measured load permits. A leased worker can run in the existing deployment topology; do not rely solely on an in-memory timer, particularly across replicas/revisions.

Growth calculates occupancy, conversion, utilization and money per currency using explicit denominators/time windows. Distinguish observed revenue, hypothetical revenue and assumptions; do not multiply vacant seats by arbitrary prices. Twin uses versioned read snapshots, typed scenario parameters and deterministic equations. No write-back path from simulation to production. Causal marketing/retention claims need evidence; show uncertainty and missing data instead of fabricated forecasts.

Automation Rate remains a proposed metric. Define eligible completed business outcomes as denominator; successful outcomes completed without human execution as numerator. Count one business outcome, not each retry/tool call. Separate assisted, approved automation, fully automatic, failed and cancelled work. Product target 90% automation/10% manual is a direction, not a measured result.
