# Teacher media capture, upload, and viewing — requirement and gap record

Date: 2026-09-30. This records the user's expanded requirement after the [private-file reproduction](PHASE_2A_PRIVATE_FILE_REPRO.md). It is a code-inspection and test-design note, **not** proof of mobile playback or a product fix. The user wants pictures, audio, video and device recordings from Android, iOS and laptops to upload and remain viewable without routine size failures.

The user corrected the initial resource assumption, then created storage account `academydeskmedia` and container `academydesk-media` in `academydesk-prod` and approved **private Blob storage, resumable uploads, a stated 2 GB maximum, and download fallback** for files that cannot be previewed. The initial repository inspection found no Blob integration; the [private Blob foundation](TEACHER_MEDIA_BLOB_FOUNDATION.md) now adds and tests the adapter with a local emulator. The current Teacher upload still writes to local `wwwroot` until the authenticated upload/viewing routes are connected. Live privacy, managed-identity data permissions, CORS and network configuration remain unverified; user portal setup statements are not live configuration evidence.

## Current implementation

| Concern | Observed code behavior | Acceptance gap |
| --- | --- | --- |
| Teacher file picker | `apps/web/src/app/teacher/page.tsx` accepts `image/*`, `audio/*`, `video/*`, PDF, DOC and DOCX | Browser picker hints are broader than the API extension allowlist; some selectable files can be rejected after selection. Native camera/video recording options and permissions have not been tested on physical devices. |
| In-browser recording | Teacher page uses `getUserMedia({ audio: true })` plus `MediaRecorder`; it creates a filename ending in `.webm` regardless of `MediaRecorder.mimeType` | A device returning a different container can be mislabeled. In-browser video recording is not implemented. Permission denial, stop/unmount, long-recording memory use, and iOS/Android behavior are unverified. |
| API formats | `TeacherPortalController.UploadClassMaterial` allows JPG/JPEG/PNG/WebP, PDF, MP3/M4A/WAV, MP4/MOV/WebM, DOC/DOCX | Other formats, including GIF and HEIC, are rejected. Extension checks do not prove safe content or browser playability. “Any format” needs a safe download fallback, not a promise that all files can play inline. |
| Size and transfer | `[RequestSizeLimit(50_000_000)]` and `File.Length > 50_000_000` reject large requests/files; one multipart POST copies to disk | Multipart overhead can make a nominal 50 MB file exceed the request limit. No resumable/chunked transfer, retry, progress, quota or server-side media processing exists. The prior TestServer warns it cannot apply its request-body size feature, so true Kestrel/proxy size behavior remains untested. |
| Storage and access | Uploads are written beneath the API container's `wwwroot`; direct static URLs are used for viewing | [BUG-SEC-0001](../ISSUES/BUG-SEC-0001.md) is reproducibly exposed to anonymous and other-tenant callers. Inference from the Dockerfile and local filesystem write: a restarted/replaced replica may not retain this media, and a different replica may not have it. This is not suitable as durable shared media storage. |
| Viewing | The staged local file gets an image/audio/video preview based on browser MIME type; saved history offers a direct `View file`/`Listen`/`Watch` link | There is no controlled saved-media viewer, format fallback, or device playback test. The link label treats `.webm` as audio before checking video. A working HTTP file response does not prove playback or rendering on a device. |
| Failed upload | `upload()` returns normally on an HTTP error; `addFile()` clears the staged file and resets the form regardless | Retrying an unsuccessful large/mobile upload requires selecting or recording the file again. |

## Required implementation decision and acceptance checks

Implement the approved design with durable **private** shared Blob storage, a 2 GB per-file ceiling and tenant quota, resumable transfer with progress/retry, and an authenticated download/streaming route supporting Range. Inline viewing should cover explicitly tested picture/audio/video formats; unknown or unplayable formats should download safely with a clear message. Upload validation must reject dangerous/mismatched content and not assume a file extension is trustworthy. No arbitrary executable upload or unlimited storage should be exposed without a security policy.

Acceptance must include actual Android and iOS phones plus desktop browsers: native camera/photo/video selection, in-browser microphone recording where supported, MIME/extension alignment, preview before submit, successful upload and reload, playable saved media, fallback download, interrupted/resumed uploads, boundary sizes, and no staged-file loss on failure. Repeat anonymous, foreign-tenant, unpublished/revoked, ordinary GET and Range checks for each storage path. Synthetic HTTP bytes can verify transport but **cannot** certify codec playback or device capture.

This expands Phase 2B's teacher-media repair and mobile validation scope. Phase 2A's PDF-only security reproduction remains valid because the unauthorized static-file path is format-agnostic, but it does not certify the additional formats or devices. No Azure, production data, product code, or application storage configuration was changed by this note.
