## Protocol references and activation limits

Google documents the web-server refresh grant and its response shape; this internal candidate is based on that flow, not a claim of an authenticated live connection. [Google refresh documentation](https://developers.google.com/identity/protocols/oauth2/web-server#refresh).

Microsoft documents confidential-client refresh requests and replacement token handling. The candidate is limited to the current work-account Graph profile and server credential; no tenant-wide logout/session-revocation permission is added. [Microsoft authorization-code/refresh flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow#refresh-the-access-token).

OAuth permits an unchanged scope grant to omit the scope response; the local fallback uses only the protected stored scopes, never model/UI-supplied additions. [RFC 6749 sections 5.1 and 6](https://www.rfc-editor.org/rfc/rfc6749#section-6). Zoom's current public-PKCE refresh authentication/rotation remains to be independently qualified: [Zoom OAuth documentation](https://developers.zoom.us/docs/integrations/oauth/).

Before any live sender is enabled, use the existing secure HTTP handler factory (no automatic redirects, proxy/cookie shortcuts, normal TLS and bounded headers), approved registration/credential resolver, isolated grant impact, account/issuer/directory/consent/meeting-entitlement qualification and current authorization around actual execution. These fake-handler tests do not prove any of that infrastructure. Refresh does not grant permissions or activate meetings. A subsequent new authorization intent supersedes old generation/fence; it does not retry an uncertain refresh. Unknown refresh/revocation resolution and cleanup still require a separately reviewed reconciliation/retention workflow. Existing local-disconnect fencing remains usable; provider-side revocation of an unknown refresh family is not automatically claimed by this slice.
